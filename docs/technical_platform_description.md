# Техническое описание платформы VKR_ISPDn

Документ описывает фактическое состояние проекта `VKR_ISPDn` по текущему коду рабочей ветки. При расхождении README и реализации приоритет отдан backend- и frontend-коду.

## 1. Назначение платформы

`VKR_ISPDn` - клиент-серверная веб-платформа для учета и контроля информационных систем персональных данных в организациях малого бизнеса.

Тема дипломного проекта: **«Разработка системы непрерывного контроля соответствия ИСПДн требованиям информационной безопасности для организаций малого бизнеса»**.

Платформа решает прикладную задачу ведения сведений об ИСПДн, процессах обработки персональных данных, уровне защищенности, технических мерах защиты, контрольных задачах и документах. Система ориентирована на малые организации, где учет ИСПДн и подготовка документов должны выполняться в едином интерфейсе без внедрения полноценной SGRC-системы.

Центральная сущность проекта - карточка ИСПДн. Пользователь сначала выбирает конкретную ИСПДн в реестре, затем переходит в связанные разделы: процессы обработки, уровень защищенности, технические меры, ЦОД, криптографию, задачи и документы. Такой подход сохраняет контекст `ispdn_id` и не заставляет пользователя заново выбирать систему внутри каждого модуля.

## 2. Общая архитектура

Проект реализован как монорепозиторий с отдельными backend и frontend частями.

Frontend работает в браузере, строит интерфейс на React и MUI, хранит server state через TanStack Query и отправляет HTTP-запросы в backend. Backend реализован на FastAPI, публикует REST API под `/api/v1`, валидирует входные и выходные данные через Pydantic, выполняет бизнес-логику в сервисном слое и работает с PostgreSQL через SQLAlchemy 2.x. Изменения структуры БД управляются Alembic.

Генерация `.docx` документов реализована через `docxtpl`: backend берет системный шаблон `template.docx`, собирает контекст из провайдеров и возвращает сформированный файл потоком. Пользовательские docx-шаблоны через UI/API в текущей версии не загружаются.

Локальная разработка выполняется без Docker. Backend запускается через Python virtual environment, frontend - через Vite dev server, PostgreSQL используется как локально установленная СУБД. В `AGENTS.md` также закреплен `httpx` как инструмент smoke-проверок HTTP API.

Поток данных:

1. Пользователь работает во frontend.
2. Frontend отправляет HTTP-запросы в backend через `fetch` и общий `httpClient`.
3. Backend валидирует данные Pydantic-схемами.
4. Endpoint вызывает service-слой.
5. Service выполняет бизнес-логику и обращается к repository-слою.
6. Repository работает с PostgreSQL через SQLAlchemy.
7. Backend возвращает ответ во frontend.
8. Frontend обновляет кэш TanStack Query и перерисовывает интерфейс.

## 5. Backend-архитектура

Основной поток backend:

```text
endpoint -> service -> repository -> database
```

Роли слоев:

- endpoint - HTTP-контракт, зависимости FastAPI, преобразование ошибок в HTTP-ответы;
- schema - Pydantic-модели входных и выходных данных;
- service - бизнес-логика, проверки, автоматизация, файловые операции;
- repository - SQLAlchemy-запросы и сохранение данных;
- model - SQLAlchemy-модель таблицы и связей;
- domain - чистые расчеты и правила без FastAPI/SQLAlchemy;
- document_generation - генерация `.docx` документов.

Примеры сквозных потоков:

1. Создание ИСПДн: `POST /api/v1/ispdns` принимает `IspdnCreate`, `IspdnService` проверяет ответственного сотрудника, `IspdnRepository` создает карточку, `TaskAutomationService` создает системное событие и задачу заполнения технических мер.
2. Сохранение уровня защищенности: `PUT /api/v1/ispdns/{ispdn_id}/security-level` принимает форму и optional файл, `SecurityLevelService` рассчитывает рекомендуемый уровень через `security_level_algorithm.py`, сохраняет запись и синхронизирует задачи несоответствия через `TaskAutomationService`.
3. Обновление технической меры: `PUT /api/v1/ispdns/{ispdn_id}/security-measures/{measure_code}` проверяет наличие уровня защищенности, определяет статус меры по ФСТЭК N 21, требует комментарий для отклонений и может закрыть системную задачу заполнения мер.
4. Генерация документа: `POST /api/v1/documents/generate` или `POST /api/v1/ispdns/{ispdn_id}/documents/generate` выбирает `DocumentGenerator` из `DocumentRegistry`, валидирует `manual_data`, собирает контекст через `DocumentContextBuilder` и рендерит `.docx` через `DocxTemplateRenderer`.

## 6. Frontend-архитектура

Основной frontend-подход:

```text
app -> pages -> widgets -> features -> entities -> shared
```

`app` содержит роутер, провайдеры TanStack Query и MUI ThemeProvider. `pages` содержат компоненты страниц маршрутов. `widgets` отвечают за общий layout и боковую навигацию. `features` содержат формы, диалоги и пользовательские сценарии. `entities` хранят API-клиенты и типы доменных сущностей. `shared` содержит общий HTTP-клиент, валидационные утилиты и переиспользуемые UI-компоненты.

React Router используется в `frontend/src/app/router.tsx`. `/` перенаправляет на `/ispdns`. TanStack Query используется для загрузки списков, карточек и справочников, а после мутаций выполняются `invalidateQueries` или `removeQueries`. React Hook Form и Zod применяются в формах карточек, сотрудников, подразделений, процессов обработки, уровня защищенности, ЦОД, СКЗИ и документов. MUI используется для layout, таблиц, карточек, диалогов, Stepper, Select, Chips и темы.

## 7. Основные сущности данных

| Сущность | Назначение | Ключевые поля | Связи и сценарии |
|---|---|---|---|
| `OrganizationCard` | Единственная карточка организации. | `short_legal_name`, `full_legal_name`, `inn`, `ogrn`, `kpp`, `registration_address`, `registration_city`, `rkn_office_address`, ответственные сотрудники, ОКВЭДы, филиалы. | Используется в `/organization` и при генерации глобальных документов. |
| `Employee` | Сотрудник организации. | `full_name`, `position`, `document_initials`, `phone_number`, `email`, `department_id`. | Ответственные в ИСПДн, задачах и документах; справочник `/employees`. |
| `Department` | Подразделение организации. | `name`. | Связано с сотрудниками; управление реализовано на странице сотрудников. |
| `IspdnCard` | Центральная карточка ИСПДн. | `name`, `short_description`, `commissioning_date`, `decommissioning_date`, `website_url`, `responsible_employee_id`, `system_composition`, `status`. | Связана с процессами обработки, уровнем защищенности, мерами, ЦОД, СКЗИ и событиями задач. |
| `ProcessingProcess` | Канонический процесс обработки ПДн. | `purpose_name`, `processing_period`, JSONB-каталоги категорий субъектов, данных, оснований и действий, `processing_type`, признаки передач, `process_signature`. | Глобальный реестр и many-to-many связь с ИСПДн. |
| `SecurityLevelRecord` | Запись уровня защищенности конкретной ИСПДн. | `data_categories`, `primary_data_category`, `subject_count_range`, `threat_type`, `subject_group`, `recommended_level`, `actual_level`, обоснование отклонения. | One-to-one с ИСПДн; используется техническими мерами и документами. |
| `IspdnSecurityTools` | Средства защиты, уже используемые внутри ИСПДн. | `dlp`, `siem`, `antivirus`, `ips_ids`, `firewall_utm_ngfw`, `vulnerability_scanner`, `backup_system`, `trusted_boot`, `access_control`, `physical_security`, `other_security_tools`. | One-to-one с ИСПДн; вводятся в карточке и wizard. |
| `TechnicalSecurityMeasureRecord` | Фактический статус меры ФСТЭК N 21 для ИСПДн. | `measure_code`, `factual_status`, `comment`. | Связана с ИСПДн; статус по приказу рассчитывается из уровня защищенности. |
| `TechnicalSecurityMeasureDocument` | Файл отчета/подтверждения по техническим мерам. | `file_path`, `file_name`, `file_content_type`, `file_size_bytes`. | Хранится на уровне модуля мер конкретной ИСПДн. |
| `ControlEvent` | Контрольное мероприятие. | `name`, `description`. | Используется в реестре контрольных мероприятий и ручных данных акта ввода ИСПДн. |
| `ControlEventFile` | Файл контрольного мероприятия. | `file_path`, `file_name`, `file_content_type`, `file_size_bytes`. | Загружается и удаляется через модуль контрольных мероприятий. |
| `TaskEvent` | Событие, объединяющее задачи. | `ispdn_id`, `event_type`, `source_module`, `title`, `description`, `automation_key`. | Всегда связано с ИСПДн; бывает ручным или системным. |
| `Task` | Задача внутри события. | `title`, `description`, `importance`, `deadline`, `responsible_employee_id`, `automation_key`, `status`. | Управляется в `/tasks` и в задачах конкретной ИСПДн. |
| `DataCenter` | Центр обработки данных. | `name`, страна и адрес, признак собственного ЦОД, сведения о владельце. | Глобальный реестр и many-to-many связь с ИСПДн. |
| `CryptoTool` | Средство криптографической защиты информации. | `name`, `crypto_class`, `manufacturer`, `serial_number`. | Глобальный реестр и many-to-many связь с ИСПДн. |
| `IspdnCryptographySettings` | Настройки использования криптографии в ИСПДн. | `ispdn_id`, `uses_cryptography`. | One-to-one с ИСПДн; список СКЗИ берется из связи `ispdn_crypto_tools`. |

Отдельная сущность «цель обработки» в актуальном коде не найдена: цель и период обработки хранятся внутри `ProcessingProcess` как `purpose_name` и `processing_period`.

## 9. Детальный пользовательский путь

`/` перенаправляет пользователя на `/ispdns`.

| URL | Страница | Что отображается | Доступные действия | Дальнейшие переходы |

## 10. Мастер создания ИСПДн

Актуальный список шагов находится в `frontend/src/pages/ispdn-card/IspdnCreatePage.tsx`:

| Шаг | Название | Данные и действия | API | Проверки и переход |
|---|---|---|---|---|
| 1 | Основные сведения | Название, описание, даты, сайт, ответственный сотрудник, состав ИСПДн, статус. | `POST /api/v1/ispdns` или `PUT /api/v1/ispdns/{id}`. | После успешного сохранения создается карточка и переход на шаг 2. |

| 3 | Информация о субъектах ПДн | Категории данных, группа субъектов, диапазон количества субъектов, тип угроз, фактический уровень и обоснование при отклонении. | `PUT /api/v1/ispdns/{id}/security-level`. | Backend рассчитывает рекомендуемый уровень. | 4 | Процессы обработки | Создание нового процесса или привязка существующего из глобального реестра. | `GET/POST /api/v1/ispdns/{id}/processing-processes`, `POST /link`. | Для завершения шага нужен минимум один связанный процесс. Новый уникальный процесс может создать системные задачи. |

## 12. Документы и генерация `.docx`

Генерация документов находится в `backend/app/document_generation/`.

Архитектура:

- `DocumentRegistry` хранит доступные генераторы и возвращает генератор по `code`;
- `DocumentGenerator` задает контракт документа: `code`, `title`, `description`, `requires_ispdn`, `template_path`, ручные поля, валидацию, сборку контекста и имя файла;
- `DocumentGenerationService` валидирует тип документа, проверяет `requires_ispdn`, вызывает генератор и renderer;
- `DocumentContextBuilder` агрегирует context providers для организации, сотрудников, ИСПДн, процессов, уровня, мер, РКН и глобальных документов;
- `DocxTemplateRenderer` использует `docxtpl.DocxTemplate` и `autoescape=True`;
- каждый системный документ лежит в `backend/app/document_generation/documents/<document_code>/` и содержит `generator.py`, `schemas.py`, `template.docx`.

Frontend получает список типов через `GET /api/v1/document-types`. Глобальная страница `/documents` показывает только документы, у которых `requires_ispdn = false`. Страница `/ispdns/:ispdnId/documents` показывает документы конкретной ИСПДн, но вход в нее из карточки ИСПДн скрыт.

| Code | Название | `requires_ispdn` | Источники данных | Ручные данные | Endpoint генерации |
|---|---|---:|---|---|---|
| `act_ispdn_commissioning` | Акт ввода ИСПДн | true | Организация, ИСПДн, контрольные мероприятия, сотрудники. | Описание нарушений и недостатков, рекомендации, список мероприятий с `control_event_id` и `responsible_employee_id`. | `POST /api/v1/ispdns/{id}/documents/generate`. |
| `act_safety_level_of_ISPDn` | Акт оценки необходимого уровня защищенности ИСПДн | true | Организация, ИСПДн, уровень защищенности, сотрудники комиссии. | `commission_members` со списком `employee_id`. | `POST /api/v1/ispdns/{id}/documents/generate`. |
| `RKN_notification` | Уведомление в Роскомнадзор об обработке ПДн | false | Организация, действующие ИСПДн, уникальные процессы обработки, ЦОД, СКЗИ, ответственные лица. | `rkn_access_persons` - лица/организации с доступом к ПДн в ГИС/МИС. | `POST /api/v1/documents/generate`. |
| `PDn_security` | Положение об организации и обеспечении защиты ПДн | false | Карточка организации и системный контекст. | `order_number`. | `POST /api/v1/documents/generate`. |
| `PDn_document` | Положение об обработке персональных данных | false | Карточка организации, процессы обработки и системный контекст. | `order_number`. | `POST /api/v1/documents/generate`. |

В текущем коде `PDn_document` и `PDn_security` зарегистрированы в `DocumentRegistry` и имеют frontend-формы в `globalDocumentFormRegistry`.

## 13. Задачи и несоответствия

Модуль задач построен вокруг двух сущностей: `TaskEvent` и `Task`.

`TaskEvent` фиксирует событие, к которому относятся задачи. В текущей модели событие обязательно связано с ИСПДн через `ispdn_id`. Событие содержит `event_type`, `source_module`, заголовок, описание и optional `automation_key`. Ручные события создаются через frontend и имеют `event_type = manual`, `source_module = manual`, `automation_key = null`.

`Task` хранит конкретную задачу: заголовок, описание, важность, дедлайн, ответственного сотрудника, статус и optional `automation_key`. Статусы: `pending`, `in_progress`, `done`. Важность: `low`, `medium`, `high`, `critical`.

Frontend `/tasks` поддерживает:

- фильтрацию по ИСПДн, статусу, важности и ответственному;
- скрытие выполненных задач по умолчанию через `actual_only=true`;
- чекбокс отображения выполненных задач;
- ручное создание событий;
- добавление, редактирование и удаление задач внутри события;
- раскрытие и скрытие списка задач события;
- быстрые Select-контролы для статуса и важности;
- переход из события к карточке ИСПДн.

Системные события и задачи, реализованные в `TaskAutomationService`:

| Событие | `event_type` | `automation_key` события | Задачи |
|---|---|---|---|
| Создание новой ИСПДн | `ispdn_created` | `ispdn_created:{ispdn_id}` | `fill_technical_security_measures` - заполнить технические меры защиты. |
| Изменение фактического уровня защищенности | `actual_security_level_changed` | Не задается, создается новое событие | `review_technical_security_measures` - пересмотреть технические меры защиты. |
| Несовпадение уровня без файла | `security_level_mismatch_without_file` | `security_level_mismatch_without_file:{ispdn_id}` | `add_security_level_deviation_file` - добавить файл обоснования отклонения. |
| Создание нового процесса обработки | `processing_process_created` | `processing_process_created:{ispdn_id}:{process_id}` | `send_rkn_notification`, `issue_pdn_processing_policy`. |

## 15. Ограничения текущей версии

- Авторизация, роли и права доступа в коде не реализованы.
- Docker/Docker Compose отсутствует и по правилам проекта не используется на этапе локальной разработки.
- CI/CD в проекте не обнаружен.
- Платформа не является полноценной SGRC-системой; реализован прикладной контур учета ИСПДн, задач, мер и документов.
- Модель угроз представлена frontend-заглушкой, отдельные модели БД и endpoint-ы для нее не найдены.
- События задач в текущей модели обязательно привязаны к ИСПДн; глобальные события без ИСПДн моделью не поддержаны.
- Пользовательские `.docx` шаблоны через UI/API не загружаются.
- Таблица технических мер не рассчитывается без сохраненной записи уровня защищенности.
- Часть файлов хранится локально в `backend/storage/...`; по коду это не отдельное объектное хранилище.

## 16. Итоговая схема работы платформы

```text
Организация -> Реестр ИСПДн -> Карточка ИСПДн -> Модули ИСПДн -> Автоматические задачи -> Документы
```

Сначала заполняется карточка организации и справочники сотрудников, ЦОД, СКЗИ и контрольных мероприятий. Затем пользователь создает или открывает карточку ИСПДн и работает с ее связанными данными: процессами обработки, уровнем защищенности, техническими мерами, ЦОД, криптографией и задачами.

Автоматизация связывает изменения в модулях с задачами контроля: создание ИСПДн, новый процесс обработки, изменение уровня защищенности и несоответствие уровня без файла создают или закрывают задачи. Документы формируются на основе сохраненных данных и ручных полей, поэтому итоговый контур работы сводится к накоплению структурированных сведений об ИСПДн и выпуску подтверждающих `.docx` документов.
