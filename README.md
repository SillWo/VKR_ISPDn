# Платформа учёта и контроля ИСПДн

## 1. Назначение проекта

Проект представляет собой клиент-серверную веб-платформу для малого бизнеса, предназначенную для ведения реестра ИСПДн, хранения связанных данных по каждой ИСПДн, контроля заполненности сведений, определения уровня защищённости, учёта технических мер защиты, фиксации задач и несоответствий, а также подготовки документов на основе уже введённых данных.

Платформа не является полноценной SGRC-системой и не должна разрабатываться как тяжёлый корпоративный продукт. Это минимальная система учёта и контроля ИСПДн для дипломного проекта.

Главная архитектурная идея: пользователь работает не с абстрактными модулями, а с данными конкретной ИСПДн. Сначала пользователь открывает карточку ИСПДн, затем переходит в связанные модули, где отображаются данные именно выбранной ИСПДн.

## 2. Зафиксированный стек проекта

### Backend

- Python
- FastAPI
- REST API
- OpenAPI
- PostgreSQL
- SQLAlchemy 2.x
- Alembic
- Pydantic

### Frontend

- React
- Vite
- TypeScript
- MUI
- React Router
- TanStack Query
- React Hook Form
- Zod

### API contract

- Источник контракта API: OpenAPI, генерируемый FastAPI.
- Orval можно подключить позже, после стабилизации базовых endpoint-ов.
- На первом этапе не подключать Orval без отдельной задачи.

### Локальная разработка

На этапе разработки Docker не используется.

Backend запускается локально через Python virtual environment.

Frontend запускается локально через Vite dev server.

PostgreSQL запускается локально как обычная установленная СУБД.

Docker Compose будет добавлен позже отдельной задачей для упаковки, временного хостинга и демонстрации на защите диплома.

## 3. Жёсткие ограничения по стеку

ИИ-агент не должен самовольно менять стек проекта.

Запрещено:

- заменять FastAPI на Django, Flask, Litestar или другой backend-фреймворк;
- заменять PostgreSQL на SQLite, MySQL, MongoDB или другую БД;
- заменять SQLAlchemy на Tortoise ORM, Prisma, Django ORM или другой ORM;
- убирать Alembic из backend-архитектуры;
- заменять React + Vite на Next.js, Remix, Vue, Angular или Svelte;
- заменять TypeScript на JavaScript;
- заменять MUI на Tailwind, shadcn/ui, Bootstrap или другую UI-библиотеку;
- заменять TanStack Query на ручное хранение server state в глобальном store;
- заменять React Hook Form + Zod на другую систему форм без отдельного решения;
- добавлять Docker на этапе локальной разработки;
- подключать Orval до стабилизации базовых endpoint-ов;
- добавлять вспомогательные библиотеки без необходимости и без отдельного обоснования.

Если задача требует нового инструмента, агент должен не внедрять его сразу, а явно указать необходимость отдельного решения.

## 5. Backend-архитектура

Backend отвечает за:

- хранение данных платформы;
- REST API для frontend;
- валидацию входных и выходных данных;
- бизнес-логику модулей ИСПДн;
- расчёт уровня защищённости;
- работу с задачами и несоответствиями;
- подготовку данных для генерации документов;
- миграции структуры БД.

### 5.2. Правила backend

- `models/` содержит только SQLAlchemy-модели.
- `schemas/` содержит только Pydantic-схемы для входных и выходных данных API.
- `api/v1/endpoints/` содержит endpoint-ы FastAPI.
- `services/` содержит бизнес-логику.
- `repositories/` содержит операции работы с БД, если логика доступа к данным становится достаточно объёмной.
- `domain/` содержит доменные правила и расчёты, если они не должны зависеть от FastAPI или SQLAlchemy.
- Нельзя смешивать SQLAlchemy-модели и Pydantic-схемы в одном классе.
- Нельзя помещать сложную бизнес-логику прямо в endpoint-ы.
- Нельзя делать прямую работу с БД из frontend.

### 5.3. API

API должен быть REST API.

Все endpoint-ы должны находиться под версией `/api/v1`.

Пример маршрутов:

```text
/api/v1/organizations
/api/v1/employees
/api/v1/processing-purposes
/api/v1/ispdns
/api/v1/ispdns/{ispdn_id}
/api/v1/ispdns/{ispdn_id}/processing
/api/v1/ispdns/{ispdn_id}/security-level
/api/v1/ispdns/{ispdn_id}/security-measures
/api/v1/ispdns/{ispdn_id}/tasks
/api/v1/tasks
```

Ключевой принцип API: данные модулей процессов обработки, уровня защищённости, модели угроз и технических мер защиты должны открываться в контексте конкретной ИСПДн через `ispdn_id`.

Нельзя проектировать эти модули как полностью независимые глобальные сущности без связи с карточкой ИСПДн.

### 6.2. Правила frontend

- Все страницы должны использовать React + TypeScript.
- UI должен строиться на MUI.
- Роутинг должен строиться на React Router.
- Запросы к backend должны выполняться через TanStack Query.
- Формы должны строиться на React Hook Form.
- Клиентская валидация форм должна строиться на Zod.
- Нельзя делать запросы к API напрямую внутри случайных UI-компонентов, если для этого уже есть слой `shared/api` или feature-level API.
- Нельзя хранить server state вручную в `useState`, если данные приходят с backend и должны обновляться через API.
- Нельзя использовать MUI X Pro или MUI X Premium. Использовать только бесплатные компоненты MUI и MUI X Community, если они понадобятся.

## 7. Базовая доменная архитектура

### 7.1. Организация

Организация содержит:

- карточку организации;
- реестр сотрудников;
- реестр целей обработки;
- реестр ИСПДн.

### 7.2. Реестр ИСПДн

Реестр ИСПДн хранит карточки ИСПДн.

Каждая запись в реестре должна вести в карточку конкретной ИСПДн.

Реестр должен позволять пользователю видеть:

- какие ИСПДн есть в организации;
- какой у них статус;
- кто ответственный за обработку ПДн;
- какие ИСПДн работают;
- какие ИСПДн находятся в архиве.

### 7.3. Карточка ИСПДн

Карточка ИСПДн является центральной сущностью системы.

Карточка ИСПДн хранит:

1. Название ИСПДн.
2. Краткое описание.
3. Цели обработки ПДн.
4. Даты ввода и вывода в/из работы.
5. Сайт ИСПДн.
6. Ответственный в компании за обработку ПДн в этой ИСПДн.
7. Состав ИСПДн.

Карточка ИСПДн хранит конкретные значения для выбранной ИСПДн из следующих модулей:

- модуль процессов обработки;
- модуль определения уровня защищённости;
- модуль модели угроз;
- модуль технических мер защиты.

Из карточки ИСПДн пользователь должен переходить в эти модули с сохранением контекста выбранной ИСПДн.

## 8. Описание модулей платформы

### 8.1. Модуль «Процессы обработки»

Модуль хранит в себе:

1. Правовое основание для обработки:
   - описание;
   - сам документ.
2. Категории субъектов ИСПДн.
3. Перечень обрабатываемых ПДн по категориям субъектов.
4. Действия, совершаемые с ПДн в ИСПДн.
5. Тип обработки.
6. Наличие передачи по внутренней сети и по Интернету.
7. Факт трансграничной передачи.

Модуль необходим для формирования уведомления в Роскомнадзор об обработке ПДн.

Данные модуля должны принадлежать конкретной карточке ИСПДн.

### 8.2. Модуль «Уровень защищённости»

Модуль хранит в себе:

1. Категории обрабатываемых ПДн.
2. Категории субъектов ПДн:
   - сотрудники;
   - клиенты.
3. Количество субъектов ПДн.
4. Тип актуальных угроз:
   - либо берётся из модуля модели угроз;
   - либо прописывается вручную в этом модуле.

На основе полученных данных модуль рассчитывает необходимый уровень защищённости.

Пользователь может выбрать другой уровень с обязательным пояснением.

Данные модуля должны принадлежать конкретной карточке ИСПДн.

### 8.3. Модуль «Технические меры защиты»

Модуль получает данные о выбранном уровне защищённости и предоставляет матрицу рекомендуемых технических мер согласно Приказу ФСТЭК №21.

Пользователь может:

1. Указать, какие меры были реализованы, описать как они были реализованы и подготовить отчётный документ.
2. Указать, какие дополнительные меры были реализованы.
3. Указать, какие рекомендуемые меры не были реализованы, и пояснить решение.

Данные модуля должны принадлежать конкретной карточке ИСПДн.

Если рекомендуемая техническая мера не реализована и пользователь не указал пояснение, это должно считаться несоответствием.

### 8.4. Модуль «Модель угроз»

Модуль потенциальный.

На данный момент модуль планируется для хранения модели актуальных угроз ИСПДн. Сама система модель угроз не может разработать, но может предложить набор агентств, предлагающих свои услуги по моделированию угроз.

На текущем этапе не расписывать детальную структуру и функционал этого модуля без отдельной задачи.

### 8.5. Контрольные мероприятия

Модуль потенциальный.

В данном модуле пользователь сможет:

1. Вести реестр контрольных мероприятий: указывать название, цель и задачи.
2. Назначать задачи по проведению контрольных мероприятий в модуль задач.
3. Назначать ответственного за проведение мероприятия, даты проведения.
4. Подготавливать отчётные документы.

Модуль потенциальный. Очень важно понять полную процедуру этих мероприятий, какие они бывают и зачем их проводить.

На текущем этапе не расписывать детальную структуру и функционал этого модуля без отдельной задачи.

### 8.6. Задачи и несоответствия

Модуль предназначен для автоматического и ручного создания задач по контролю ИСПДн.

Модуль сам сможет создавать задачи, связанные:

1. С проведением контрольных мероприятий.
2. С незаполненными обязательными полями карточек ИСПДн.
3. С процедурой подачи уведомления в РКН об инциденте.
4. С необъяснёнными несоответствиями:
   - нереализованные рекомендуемые технические меры без объяснения;
   - пониженный или повышенный уровень защищённости без объяснения.

Помимо автоматического добавления задач пользователь сам может создавать задачи по работе с ИСПДн.

### 8.7. Документация

Модуль не выражен в отдельной странице, а является встроенным механизмом по генерации документов.

Потенциально он может выступать как единый реестр всех документов, связанных с ИСПДн.

На текущем этапе документация должна рассматриваться как встроенный механизм, который использует данные из уже созданных модулей.

### 8.8. Реестр целей обработки

Вспомогательный модуль, который хранит цели обработки, созданные организацией.

Каждая цель содержит:

1. Название.
2. Период обработки.

Цель обработки является составляющей процесса обработки, который нужен для отправки в РКН уведомления об обработке ПДн.

### 8.9. Карточка организации

Вспомогательный модуль, который хранит информацию об организации пользователя.

Карточка организации хранит:

1. Сокращённое название юридического лица.
2. Полное название юридического лица.
3. ИНН.
4. ОГРН.
5. КПП.
6. ФИО руководителя.
7. Должность руководителя.
8. Адрес регистрации.
9. Город регистрации.

### 8.10. Реестр сотрудников

Вспомогательный модуль, который хранит карточки сотрудников организации.

Карточка сотрудника содержит:

1. ФИО сотрудника.
2. Должность.
3. Подразделение.

Эти данные нужны для указания ответственных в документах.

## 9. Навигационная архитектура

Основные разделы платформы:

1. Реестр ИСПДн.
2. Карточка конкретной ИСПДн.
3. Карточка организации.
4. Реестр сотрудников.
5. Реестр целей обработки.
6. Задачи и несоответствия.
7. Документы, если будет реализован единый реестр документов.

Внутри карточки конкретной ИСПДн должны быть доступны подразделы:

1. Основные сведения.
2. Процессы обработки.
3. Уровень защищённости.
4. Модель угроз.
5. Технические меры защиты.
6. Задачи и несоответствия по этой ИСПДн.
7. Документы по этой ИСПДн.
8. Контрольные мероприятия, если модуль будет реализован.

Ключевой принцип навигации: пользователь сначала выбирает ИСПДн, затем работает с её данными.

Пользователь не должен заново выбирать ИСПДн внутри каждого модуля. Контекст выбранной ИСПДн должен передаваться через маршрут и идентификатор `ispdn_id`.

Агент должен строго следовать этому README как базовому архитектурному документу проекта.

Перед выполнением любой задачи агент должен учитывать:

- зафиксированный стек;

Агент должен сохранять уже принятую архитектуру и не переписывать существующую структуру без прямого указания.

## 11. Правила локального запуска

### Backend

Backend должен запускаться локально через virtual environment.

Общий подход:

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Для Linux/macOS активация окружения:

```bash
source .venv/bin/activate
```

### Frontend

Frontend должен запускаться через Vite dev server.

Общий подход:

```bash
cd frontend
npm install
npm run dev
```

### Database

PostgreSQL должен быть установлен и запущен локально.

Подключение к БД должно выполняться через переменные окружения.

Пример переменных окружения должен храниться в `.env.example`.

В репозиторий нельзя добавлять реальные пароли, токены и локальные секреты.

## 12. Правила работы с миграциями

Все изменения структуры БД должны проходить через Alembic.

Запрещено менять структуру БД вручную без миграций, если проект уже использует Alembic.

Миграции должны быть понятными по названию и отражать сделанное изменение.

## 13. Правила работы с обязательными полями

Все поля, перечисленные в этом README, являются обязательной минимальной структурой.

Поля можно дополнять, но нельзя удалять, сокращать или игнорировать.

Это касается:

- карточки ИСПДн;
- процессов обработки;
- уровня защищённости;
- технических мер защиты;
- модели угроз;
- задач и несоответствий;
- документации;
- карточки организации;
- реестра сотрудников;
- реестра целей обработки.

## 14. Текущее правило по Docker

На этапе разработки Docker не используется.

Не создавать:

- Dockerfile;
- docker-compose.yml;
- compose.yaml;
- контейнеры для PostgreSQL;
- контейнеры для backend;
- контейнеры для frontend.

Docker Compose будет добавлен позже отдельной задачей, когда базовая версия приложения будет стабильно работать локально.

## 15. Итоговое правило проекта

Проект должен развиваться поэтапно.

Одна задача для ИИ-агента должна изменять одну ограниченную часть системы.

Главный приоритет — сохранить понятную клиент-серверную архитектуру, где backend предоставляет REST API, frontend работает с ним через HTTP-запросы, а все данные по процессам обработки, уровню защищённости, модели угроз и техническим мерам защиты принадлежат конкретной карточке ИСПДн.
