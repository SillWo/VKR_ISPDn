# DESIGN.md

## 1. Назначение файла

Этот файл задаёт визуальные правила интерфейса для проекта `VKR_ISPDn`.

Проект — административная веб-платформа для учёта и контроля ИСПДн. Интерфейс должен выглядеть спокойно, строго и технически аккуратно. Это не лендинг, не маркетинговый сайт и не экспериментальный UI. Это рабочая система с реестрами, карточками, формами, статусами, задачами, несоответствиями и документами.

Дизайн базируется на стиле `Column — Style Reference`, адаптированном под проект `VKR_ISPDn` и стек React + MUI.

Основная визуальная идея:

> Светлая административная система с ощущением технической точности: белая и светло-серая основа, тонкие границы, аккуратные карточки, строгая типографика, мягкие тени и точечные акценты для важных действий.

---

## 2. Главные принципы UI

Интерфейс должен быть:

- светлым;
- спокойным;
- структурным;
- читаемым;
- административным;
- пригодным для длинных форм и таблиц;
- без визуального шума;
- без ярких случайных цветов;
- без декоративной перегрузки.

Интерфейс не должен выглядеть как:

- лендинг;
- игровой интерфейс;
- маркетинговый SaaS;
- тёмная developer-панель;
- экспериментальный дизайн-концепт;
- Bootstrap-админка из коробки.

Главный приоритет — удобная работа с данными ИСПДн.

## 3. Технологические ограничения

Проект использует MUI.

Все визуальные правила должны реализовываться через:

- `@mui/material`;
- `createTheme`;
- `ThemeProvider`;
- `CssBaseline`;
- MUI-компоненты;
- локальные переиспользуемые компоненты в `shared/ui`.

Запрещено:

- подключать Tailwind;
- подключать shadcn/ui;
- подключать Bootstrap;
- подключать Ant Design;
- подключать Chakra UI;
- использовать MUI X Pro;
- использовать MUI X Premium;
- добавлять новые UI-библиотеки без отдельной задачи;
- подключать сторонние платные шрифты;
- загружать или хранить font-файлы в репозитории.

Если нужен Data Grid, использовать только бесплатный пакет:

```text
@mui/x-data-grid
```

Запрещено использовать:

```text
@mui/x-data-grid-pro
@mui/x-data-grid-premium
```

## 6. Типографика

### 6.1. Основной шрифт

Использовать `Inter`.

Причина: исходный стиль Column использует SuisseIntl, но для проекта нельзя подключать платные или нестандартные шрифты. Inter указан как допустимая замена и хорошо подходит для административного интерфейса.

Основной font stack:

```css
font-family: Inter, ui-sans-serif, system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Arial, sans-serif;
```

### 6.2. Моноширинный шрифт

Для технических значений, кодов, идентификаторов, ИНН, ОГРН, КПП и служебных значений использовать системный monospace stack:

```css
font-family: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, "Liberation Mono", "Courier New", monospace;
```

### 6.3. Размеры текста

| Роль | Размер | Вес | Line height | Применение |
|---|---:|---:|---:|---|
| caption | 12px | 400 | 1.5 | Подписи, служебный текст |
| body-sm | 13px | 400 | 1.5 | Таблицы, компактные блоки |
| body | 14px | 400 | 1.5 | Основной текст интерфейса |
| body-md | 16px | 400 | 1.5 | Описания, пустые состояния |
| section-title | 18px | 600 | 1.4 | Заголовки секций |
| page-title | 24px | 600 | 1.33 | Заголовки страниц |
| display | 32px | 600 | 1.2 | Крупные заголовки стартовых экранов |

Для административной платформы не использовать огромные заголовки 48–60px, кроме специальных стартовых экранов. В рабочих модулях достаточно 24–32px.

## 8. Радиусы и тени

### Радиусы

| Элемент | Радиус |
|---|---:|
| Карточки | 8px |
| Кнопки | 8px |
| Поля ввода | 8px |
| Таблицы / контейнеры таблиц | 8px |

| Диалоги | 12px |

### Тени

Использовать мягкие тени и тонкие границы.

Основная тень карточки:

```css
box-shadow:
  rgba(17, 26, 74, 0.05) 0px 0px 0px 1px,
  rgba(0, 0, 0, 0.08) 0px 1px 2px 0px,
  rgba(255, 255, 255, 0.5) 0px 0px 0px 1px inset;
```

```css
box-shadow:
  rgba(0, 0, 0, 0.06) 0px 8px 24px,
  rgba(17, 26, 74, 0.08) 0px 0px 0px 1px;
```

Запрещены тяжёлые, тёмные и драматичные тени.

## 9. Layout

### 9.1. Общий layout приложения

Базовый интерфейс должен состоять из:

- верхней панели или боковой навигации;
- основной рабочей области;
- заголовка страницы;
- контентной зоны;
- карточек, таблиц и форм.

Рекомендуемый вариант для платформы:

```text
Left sidebar + top page header + main content
```

Боковая навигация хорошо подходит, потому что в системе несколько постоянных разделов:

- Реестр ИСПДн;
- Карточка организации;
- Реестр сотрудников;
- Реестр целей обработки;
- Задачи и несоответствия;
- Документы.

### 9.2. Ширина контента

Рабочая область должна быть ограничена по максимальной ширине, чтобы формы не растягивались слишком широко.

Рекомендуемые значения:

```text
max-width: 1200–1280px
```

Для страниц с таблицами можно использовать всю доступную ширину рабочей области.

### 9.3. Фон

Фон приложения:

```text
Fog Gray — #f6f6f8
```

Фон карточек:

```text
Ghost White — #ffffff
```

Фон вложенных секций:

```text
#ffffff или #f6f6f8
```

## 10. Blueprint background

Исходный стиль Column использует лёгкую техническую grid-подложку. В проекте её можно использовать только умеренно.

Разрешено использовать subtle grid:

- на стартовой странице;
- в пустых состояниях;
- в верхней части dashboard;
- в информационных callout-блоках.

Не использовать grid внутри форм, таблиц и карточек с большим количеством данных.

Пример CSS:

```css
background-image:
  radial-gradient(rgba(2, 50, 71, 0.12) 1px, transparent 1px);
background-size: 18px 18px;
```

Для рабочих экранов grid должен быть почти незаметным.

## 11. Компоненты

Основной layout:

Состав:

- название страницы;
- короткое описание;
- основные действия справа;
- breadcrumbs при необходимости.

Пример:

```text
Реестр ИСПДн
Список информационных систем персональных данных организации
[Создать ИСПДн]
```

Заголовок:

```text
24px / 600 / Ink Blue
```

```text
14px / 400 / Slate Text
```

## 11.3. Cards

Карточки используются для:

- карточки ИСПДн;
- блоков формы;
- кратких сводок;
- статусов;
- пустых состояний;
- группировки полей.

Стиль карточки:

```text

border: 1px solid #e3e4e8
border-radius: 8px

```

Карточка не должна быть визуально тяжёлой.

---

## 11.4. Tables

Таблицы используются для:

- реестра ИСПДн;
- сотрудников;
- целей обработки;
- задач;
- документов;
- технических мер.

Стиль таблиц:

- белый фон;
- тонкие границы;
- компактная, но читаемая высота строк;
- заголовок таблицы на `Fog Gray`;
- основной текст `Charcoal Text`;
- вторичный текст `Slate Text`;
- действия в строках не должны перегружать таблицу.

Рекомендуемая высота строки:

```text
48–56px
```

Заголовок таблицы:

```text
font-size: 12px
font-weight: 600
color: #7c7f88
text-transform: none
background: #f6f6f8
```

Не использовать плотность, при которой данные становятся нечитаемыми.

## 11.5. Forms

Формы — ключевая часть системы.

Формы должны быть:

- разделены на смысловые секции;
- не перегружены одним огромным полотном;
- с понятными labels;
- с поясняющим helper text там, где поле юридически или методически сложное;
- с явными ошибками валидации.

Поля формы:

```text
border-radius: 8px
background: #ffffff
```

Labels:

```text
font-size: 14px
font-weight: 500
color: #232730
```

Helper text:

```text
font-size: 12px
color: #7c7f88
```

Ошибки:

```text
color: #d14343
```

Для больших форм использовать секции:

```text
Основные сведения
Правовые основания
Категории субъектов
Перечень ПДн
Передача данных
```

## 11.8. Alerts

Alert должен быть спокойным и информационным.

Не делать alerts слишком яркими.

Типы:

- info;
- success;
- warning;
- error.

Warning и error использовать только когда есть реальная проблема:

- обязательное поле не заполнено;
- мера не реализована без пояснения;
- уровень защищённости изменён без пояснения;
- данные не готовы для документа.

---

## 11.9. Empty States

Пустые состояния нужны для разделов, где ещё нет данных.

Структура:

- короткий заголовок;
- понятное объяснение;
- одно основное действие;
- без декоративной перегрузки.

Пример:

```text
ИСПДн ещё не добавлены
Создайте первую карточку ИСПДн, чтобы начать вести сведения о системе и связанных процессах обработки.
[Создать ИСПДн]
```

Пустые состояния можно размещать на карточке с лёгким grid-фоном.

---

## 11.10. Dialogs

Диалоги использовать для:

- подтверждения удаления;
- коротких форм;
- создания небольших сущностей;
- предупреждений.

Не использовать modal dialog для больших многоразделных форм. Большие формы должны быть отдельными страницами или секциями карточки.

Стиль:

```text
border-radius: 12px
background: #ffffff
padding: 24px
```

## 12. Страницы платформы

## 12.1. Реестр ИСПДн

Страница должна выглядеть как рабочий реестр.

Основные элементы:

- page header;
- кнопка создания ИСПДн;
- фильтры;
- таблица ИСПДн;
- статусы;
- быстрый переход в карточку.

Не делать карточки вместо таблицы для основного реестра, если записей потенциально много.

Рекомендуемые колонки:

- Название;
- Статус;
- Ответственный;
- Цели обработки;
- Дата ввода;
- Дата вывода;
- Действия.

---

## 12.2. Карточка ИСПДн

Карточка ИСПДн должна быть центральным рабочим экраном.

Верхняя часть:

- название ИСПДн;
- статус;
- краткое описание;
- ответственный;
- быстрые действия.

Далее:

- вкладки или боковая навигация внутри карточки;
- основные сведения;
- процессы обработки;
- уровень защищённости;
- модель угроз;
- технические меры;
- задачи;
- документы.

Внутри карточки пользователь должен понимать, что он работает с конкретной ИСПДн.

---

## 12.3. Процессы обработки

Экран должен быть формой или набором карточек с секциями:

- правовое основание;
- категории субъектов;
- перечень ПДн;
- действия с ПДн;
- тип обработки;
- передача по сети и интернету;
- трансграничная передача.

Сложные поля должны иметь helper text.

---

## 12.4. Уровень защищённости

Экран должен показывать:

- входные параметры;
- рассчитанный уровень;
- выбранный пользователем уровень;
- пояснение при изменении уровня;
- предупреждение, если пояснения нет.

Рассчитанный уровень должен быть визуально заметен, но без агрессивного оформления.

---

## 12.5. Технические меры защиты

Экран должен быть табличным или карточно-табличным.

Для каждой меры показывать:

- код или название меры;
- рекомендация;
- статус реализации;
- описание реализации;
- пояснение, если не реализована.

Нереализованная мера без пояснения должна быть выделена как несоответствие.

---

## 12.6. Задачи и несоответствия

Экран должен быть похож на административный список задач.

Основные элементы:

- фильтры;
- статусы;
- источник задачи;
- связанная ИСПДн;
- ответственный;
- срок;
- действия.

## 17. Правила для Codex

## 17.1. Постоянные правила UI-паттернов

Эти правила применяются ко всем страницам, формам, карточкам, модальным окнам, мастерам создания, реестрам и внутренним модулям платформы.

1. Бинарные поля отображаются через `Checkbox`, а не через `Switch` с вариантами «Да» / «Нет». `checked` означает `true` / «Да», unchecked означает `false` / «Нет». Имена полей, payload и backend-логику менять нельзя.
2. В `TextField`, `Select`, `Autocomplete` и похожих MUI-полях текст, placeholder и label должны быть визуально выровнены по центру высоты outlined-поля. Основное решение должно находиться в MUI theme overrides или общем shared UI-паттерне.
3. Крупные смысловые блоки основного контента не должны разделяться жёсткими рамками. Основное разделение строится через внешний отступ, внутренний padding, фон, мягкую тень и иерархию. Границы допустимы для полей ввода, таблиц, row separators, focus/error states.
4. Кнопки «Назад» и «Далее» размещаются рядом. «Далее» является primary action, «Назад» соседним навигационным действием, второстепенные действия не должны визуально конкурировать с ними.
5. Для переключения смысловых разделов внутри одной формы, страницы или модуля используются MUI `Tabs` / `Tab`. В tabbed-формах должны быть «Назад» и «Далее»: на первом tab «Назад» disabled или скрыта, на последнем tab «Далее» заменяется финальным действием формы. При переходе на tab контент открывается с начала, а «Далее» валидирует текущий tab.

Перед изменением UI Codex должен прочитать:

1. `AGENTS.md`.
2. `README.md`.
3. `DESIGN.md`.
4. Файлы frontend, относящиеся к задаче.

Codex обязан соблюдать:

- стек проекта;
- MUI как единственную UI-библиотеку;
- светлую тему;
- токены из этого файла;
- структуру frontend;
- запрет на Tailwind/shadcn/Bootstrap;
- запрет на MUI X Pro/Premium.

Если задача просит сделать UI без указания стиля, использовать этот `DESIGN.md` как источник истины.

Если задача противоречит `DESIGN.md`, остановиться и явно указать конфликт.

## 18. Главное правило дизайна

Интерфейс должен помогать пользователю спокойно вести данные по ИСПДн.

Визуальный стиль не должен отвлекать от работы с реестрами, карточками, формами, статусами, задачами и документами.

Дизайн должен создавать ощущение:

```text
точность, порядок, контроль, юридическая аккуратность, техническая надёжность
```
