# AGENTS.md

## 1. Назначение файла

Этот файл содержит обязательные инструкции для ИИ-агента Codex при работе с проектом `VKR_ISPDn`.

README.md должен оставаться человекочитаемым описанием проекта: назначение, запуск, структура и общая логика.

AGENTS.md должен использоваться как техническая инструкция для агента: правила работы, ограничения, структура изменений, проверки и запреты.

Перед началом любой задачи агент обязан прочитать:

1. `AGENTS.md`.
2. `README.md`.
3. Текущий пользовательский промпт.
4. Файлы проекта, которые относятся к выполняемой задаче.

Если инструкция в пользовательском промпте противоречит этому файлу или README.md, агент не должен молча выбирать один вариант. Нужно остановиться и явно указать конфликт.

---

## 2. Главная цель проекта

Проект `VKR_ISPDn` — клиент-серверная веб-платформа для учёта и контроля ИСПДн в малом бизнесе.

Главная доменная идея:

Пользователь работает не с абстрактными модулями, а с данными конкретной ИСПДн.

Базовый сценарий:

1. Пользователь открывает реестр ИСПДн.
2. Пользователь выбирает карточку конкретной ИСПДн.
3. Из карточки ИСПДн пользователь переходит в связанные модули.
4. В связанных модулях отображаются и редактируются данные именно выбранной ИСПДн.

Карточка ИСПДн является центральной сущностью системы.

## 3. Зафиксированный стек

### Backend

Использовать только:

- Python
- FastAPI
- REST API
- OpenAPI
- PostgreSQL
- SQLAlchemy 2.x
- Alembic
- Pydantic

### Frontend

Использовать только:

- React
- Vite
- TypeScript
- MUI
- React Router
- TanStack Query
- React Hook Form
- Zod

### Локальная разработка

На этапе разработки Docker не используется.

Backend запускается через Python virtual environment.

Frontend запускается через Vite dev server.

PostgreSQL используется как локально установленная СУБД.

Docker Compose будет добавлен позже отдельной задачей только для упаковки, временного хостинга и демонстрации на защите диплома.

- использовать Axios без отдельной задачи;
- подключать Orval до стабилизации базовых endpoint-ов;

Если для выполнения задачи реально нужен новый инструмент или библиотека, агент должен сначала явно указать это в финальном отчёте или остановиться, если без этого невозможно продолжить. Нельзя внедрять новый инструмент молча.

## 7. Backend-правила

Backend отвечает за:

* REST API для frontend;
* хранение данных;
* валидацию входных и выходных данных;
* бизнес-логику модулей;
* расчёты;
* работу с БД;
* миграции;
* подготовку данных для документов.

### 7.1. Правила слоёв backend

`models/` содержит только SQLAlchemy-модели.

`schemas/` содержит только Pydantic-схемы для входных и выходных данных API.

`api/v1/endpoints/` содержит FastAPI endpoint-ы.

`services/` содержит бизнес-логику.

`repositories/` содержит операции доступа к БД, если логика работы с данными становится достаточно объёмной.

`domain/` содержит доменные правила и расчёты, которые не должны зависеть от FastAPI или SQLAlchemy.

`core/` содержит конфигурацию, подключение к БД и базовые настройки приложения.

### 7.2. Запреты backend

Нельзя смешивать SQLAlchemy-модели и Pydantic-схемы в одном классе.

Нельзя помещать сложную бизнес-логику прямо в endpoint-ы.

Нельзя создавать таблицы автоматически при старте приложения, если уже используется Alembic.

Нельзя менять структуру БД без миграции Alembic после появления моделей.

Нельзя использовать sync/async вперемешку без необходимости. Если проект уже использует синхронный SQLAlchemy-подход, продолжать его до отдельного решения о смене подхода.

Нельзя добавлять бизнес-сущности, которые не требуются текущей задачей.

### 7.3. API-правила

Все endpoint-ы должны быть под версией:

```text
/api/v1
```

Ключевой принцип API:

Данные модулей, принадлежащих конкретной ИСПДн, должны открываться через `ispdn_id`.

Примеры правильных маршрутов:

```text
/api/v1/ispdns/{ispdn_id}/processing
/api/v1/ispdns/{ispdn_id}/security-level
/api/v1/ispdns/{ispdn_id}/security-measures
/api/v1/ispdns/{ispdn_id}/tasks
```

Нельзя проектировать процессы обработки, уровень защищённости, модель угроз и технические меры защиты как полностью независимые глобальные сущности без связи с карточкой ИСПДн.

## 8. Frontend-правила

Frontend отвечает за:

* интерфейс реестра ИСПДн;
* интерфейс карточки ИСПДн;
* переходы в модули конкретной ИСПДн;
* формы создания и редактирования данных;
* отображение статусов, задач и несоответствий;
* работу с REST API backend;
* клиентскую валидацию форм.

### 8.1. Правила слоёв frontend

`src/app/` содержит инициализацию приложения, роутер и провайдеры.

`src/pages/` содержит страницы маршрутов.

`src/widgets/` содержит крупные UI-блоки: layout, navigation, page shell.

`src/features/` содержит функциональные действия и сценарии.

`src/entities/` содержит сущности предметной области frontend-слоя.

`src/shared/` содержит переиспользуемые API-клиенты, UI-компоненты, типы и утилиты.

### 8.2. Правила frontend-разработки

Все страницы должны использовать React + TypeScript.

UI должен строиться на MUI.

Роутинг должен строиться на React Router.

Запросы к backend должны выполняться через TanStack Query.

Формы должны строиться на React Hook Form.

Клиентская валидация форм должна строиться на Zod.

Server state нельзя хранить вручную в `useState`, если данные приходят с backend и должны обновляться через API.

Запросы к API нельзя хаотично размещать в случайных UI-компонентах. Использовать слой `shared/api` или API-слой конкретной feature/entity.

### 8.3. Запреты frontend

Запрещено:

* использовать Tailwind, shadcn/ui, Bootstrap вместо MUI;
* использовать JavaScript вместо TypeScript;
* подключать Next.js или другой фреймворк поверх React + Vite;
* использовать MUI X Pro или MUI X Premium;
* добавлять сложный глобальный store без прямой задачи;
* дублировать server state в Zustand, Redux или Context без необходимости;
* делать прямое обращение frontend к БД;
* хардкодить реальные backend URL вместо переменных окружения.

## 9. Доменная архитектура

### 9.1. Организация

Организация содержит:

* карточку организации;
* реестр сотрудников;
* реестр целей обработки;
* реестр ИСПДн.

### 9.2. Реестр ИСПДн

Реестр ИСПДн хранит карточки ИСПДн.

Каждая запись реестра должна вести в карточку конкретной ИСПДн.

Реестр должен позволять пользователю видеть:

* какие ИСПДн есть в организации;
* какой у них статус;
* кто ответственный за обработку ПДн;
* какие ИСПДн работают;
* какие ИСПДн находятся в архиве.

### 9.3. Карточка ИСПДн

Карточка ИСПДн — центральная сущность системы.

Карточка ИСПДн хранит:

1. Название ИСПДн.
2. Краткое описание.
3. Цели обработки ПДн.
4. Даты ввода и вывода в/из работы.
5. Сайт ИСПДн.
6. Ответственный в компании за обработку ПДн в этой ИСПДн.
7. Состав ИСПДн.

Карточка ИСПДн хранит конкретные значения для выбранной ИСПДн из следующих модулей:

* модуль процессов обработки;
* модуль определения уровня защищённости;
* модуль модели угроз;
* модуль технических мер защиты.

Из карточки ИСПДн пользователь должен переходить в эти модули с сохранением контекста выбранной ИСПДн.

## 10. Обязательные поля модулей

Все перечисленные поля являются минимальной обязательной структурой.

Поля можно дополнять, но нельзя удалять, сокращать или игнорировать.

### 10.1. Модуль «Процессы обработки»

Модуль хранит:

1. Правовое основание для обработки:

   * описание;
   * сам документ.
2. Категории субъектов ИСПДн.
3. Перечень обрабатываемых ПДн по категориям субъектов.
4. Действия, совершаемые с ПДн в ИСПДн.
5. Тип обработки.
6. Наличие передачи по внутренней сети и по Интернету.
7. Факт трансграничной передачи.

Модуль необходим для формирования уведомления в Роскомнадзор об обработке ПДн.

Данные модуля должны принадлежать конкретной карточке ИСПДн.

### 10.2. Модуль «Уровень защищённости»

Модуль хранит:

1. Категории обрабатываемых ПДн.
2. Категории субъектов ПДн:

   * сотрудники;
   * клиенты.
3. Количество субъектов ПДн.
4. Тип актуальных угроз:

   * либо берётся из модуля модели угроз;
   * либо прописывается вручную в этом модуле.

На основе полученных данных модуль рассчитывает необходимый уровень защищённости.

Пользователь может выбрать другой уровень с обязательным пояснением.

Данные модуля должны принадлежать конкретной карточке ИСПДн.

### 10.3. Модуль «Технические меры защиты»

Модуль получает данные о выбранном уровне защищённости и предоставляет матрицу рекомендуемых технических мер согласно Приказу ФСТЭК №21.

Пользователь может:

1. Указать, какие меры были реализованы, описать как они были реализованы и подготовить отчётный документ.
2. Указать, какие дополнительные меры были реализованы.
3. Указать, какие рекомендуемые меры не были реализованы, и пояснить решение.

Данные модуля должны принадлежать конкретной карточке ИСПДн.

Если рекомендуемая техническая мера не реализована и пользователь не указал пояснение, это должно считаться несоответствием.

### 10.4. Модуль «Модель угроз»

Модуль потенциальный.

На данный момент модуль планируется для хранения модели актуальных угроз ИСПДн.

Сама система модель угроз не может разработать, но может предложить набор агентств, предлагающих свои услуги по моделированию угроз.

На текущем этапе не расписывать детальную структуру и функционал этого модуля без отдельной задачи.

### 10.5. Контрольные мероприятия

Модуль потенциальный.

В данном модуле пользователь сможет:

1. Вести реестр контрольных мероприятий: указывать название, цель и задачи.
2. Назначать задачи по проведению контрольных мероприятий в модуль задач.
3. Назначать ответственного за проведение мероприятия, даты проведения.
4. Подготавливать отчётные документы.

Модуль потенциальный. Очень важно понять полную процедуру этих мероприятий, какие они бывают и зачем их проводить.

На текущем этапе не расписывать детальную структуру и функционал этого модуля без отдельной задачи.

### 10.6. Задачи и несоответствия

Модуль предназначен для автоматического и ручного создания задач по контролю ИСПДн.

Модуль сам сможет создавать задачи, связанные:

1. С проведением контрольных мероприятий.
2. С незаполненными обязательными полями карточек ИСПДн.
3. С процедурой подачи уведомления в РКН об инциденте.
4. С необъяснёнными несоответствиями:

   * нереализованные рекомендуемые технические меры без объяснения;
   * пониженный или повышенный уровень защищённости без объяснения.

Помимо автоматического добавления задач пользователь сам может создавать задачи по работе с ИСПДн.

### 10.7. Документация

Модуль не выражен в отдельной странице, а является встроенным механизмом по генерации документов.

Потенциально он может выступать как единый реестр всех документов, связанных с ИСПДн.

На текущем этапе документация должна рассматриваться как встроенный механизм, который использует данные из уже созданных модулей.

### 10.8. Реестр целей обработки

Вспомогательный модуль, который хранит цели обработки, созданные организацией.

Каждая цель содержит:

1. Название.
2. Период обработки.

Цель обработки является составляющей процесса обработки, который нужен для отправки в РКН уведомления об обработке ПДн.

### 10.9. Карточка организации

Вспомогательный модуль, который хранит информацию об организации пользователя.

Карточка организации хранит:

1. Сокращённое название юридического лица.
2. Полное название юридического лица.
3. ИНН.
4. ОГРН.
5. КПП.
6. ФИО руководителя.
7. Должность руководителя.
8. Адрес регистрации.
9. Город регистрации.

### 10.10. Реестр сотрудников

Вспомогательный модуль, который хранит карточки сотрудников организации.

Карточка сотрудника содержит:

1. ФИО сотрудника.
2. Должность.
3. Подразделение.

Эти данные нужны для указания ответственных в документах.

## 11. Навигационная архитектура

Основные разделы платформы:

1. Реестр ИСПДн.
2. Карточка конкретной ИСПДн.
3. Карточка организации.
4. Реестр сотрудников.
5. Реестр целей обработки.
6. Задачи и несоответствия.
7. Документы, если будет реализован единый реестр документов.

Внутри карточки конкретной ИСПДн должны быть доступны подразделы:

1. Основные сведения.
2. Процессы обработки.
3. Уровень защищённости.
4. Модель угроз.
5. Технические меры защиты.
6. Задачи и несоответствия по этой ИСПДн.
7. Документы по этой ИСПДн.
8. Контрольные мероприятия, если модуль будет реализован.

Ключевой принцип навигации:

Пользователь сначала выбирает ИСПДн, затем работает с её данными.

Пользователь не должен заново выбирать ИСПДн внутри каждого модуля.

Контекст выбранной ИСПДн должен передаваться через маршрут и идентификатор `ispdn_id`.

## 12. Правила локального запуска

### 12.1. Backend

Запускать backend локально через virtual environment.

Windows PowerShell:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Linux/macOS:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

### 12.2. Frontend

Запускать frontend через Vite dev server.

```bash
cd frontend
npm install
npm run dev
```

### 12.3. Database

PostgreSQL должен быть установлен и запущен локально.

Подключение к БД должно выполняться через переменные окружения.

Пример переменных окружения должен храниться в `.env.example`.

Реальные `.env` файлы не добавлять в Git.

## 13. Проверки после изменений

Агент обязан выполнять проверки, относящиеся к изменённой части проекта.

### 13.1. Backend-проверки

После изменения backend выполнить:

```powershell
cd backend
python -m compileall app
python -c "from app.main import app; print(app.title)"
```

Если изменение затрагивает зависимости, предварительно выполнить:

```powershell
pip install -r requirements.txt
```

Если изменение затрагивает БД или модели, проверить Alembic-команды, применимые к текущей задаче.

Не создавать миграции без необходимости.

### 13.2. Frontend-проверки

После изменения frontend выполнить:

```bash
cd frontend
npm run build
```

Если изменение затрагивает зависимости, предварительно выполнить:

```bash
npm install
```

Нельзя оставлять проект в состоянии, где `npm run build` падает.

### 13.3. Full-project checks

Если задача затрагивает и backend, и frontend, нужно выполнить проверки обеих частей.

Если проверку невозможно выполнить из-за ограничений окружения, агент должен явно написать:

* какую команду не удалось выполнить;
* почему;
* какие проверки были выполнены вместо неё.

## 14. Правила работы с Git

Агент не должен создавать новые ветки, если задача этого не требует.

Агент не должен делать commit, если задача этого не требует.

Агент не должен делать push, если задача этого не требует.

Если задача требует commit:

1. Проверить `git status`.
2. Убедиться, что в commit попадут только изменения по текущей задаче.
3. Использовать короткое осмысленное сообщение commit на английском языке.

Если задача требует push:

1. Убедиться, что текущая ветка соответствует задаче.
2. Проверить remote.
3. Выполнить push только после успешных проверок.

Нельзя добавлять в Git:

* `.env`;
* `.env.local`;
* `.venv`;
* `node_modules`;
* `dist`;
* build-артефакты;
* временные файлы IDE;
* реальные секреты.

## 15. Правила работы с README.md

README.md должен быть человекочитаемым.

Не превращать README.md в длинный список агентских инструкций.

README.md должен содержать:

* назначение проекта;
* краткое описание архитектуры;
* стек;
* структуру проекта;
* правила локального запуска;
* краткое описание модулей;
* информацию, полезную человеку.

AGENTS.md должен содержать:

* правила для Codex;
* запреты;
* проверки;
* требования к структуре изменений;
* правила работы с кодом;
* stop rules.

Не редактировать README.md без прямой задачи.

## 16. Правила изменения архитектуры

Нельзя менять архитектуру проекта без прямого указания.

Нельзя переносить ответственность между backend и frontend без отдельного решения.

Нельзя превращать frontend в источник бизнес-логики.

Нельзя превращать backend endpoint-ы в место хранения всей бизнес-логики.

Нельзя делать модули процессов обработки, уровня защищённости, модели угроз и технических мер защиты глобальными сущностями без связи с ИСПДн.

Нельзя сокращать обязательные поля модулей.

Нельзя удалять потенциальные модули из архитектуры только потому, что они пока не реализуются.

## 17. Stop rules

Агент должен остановиться и сообщить проблему, если:

* не найден README.md;
* не найден AGENTS.md;
* задача противоречит зафиксированному стеку;
* задача требует Docker на этапе локальной разработки без явного решения пользователя;
* задача требует замены backend или frontend фреймворка;
* задача требует удаления обязательных полей;
* задача требует реализации сразу нескольких крупных модулей, но формулируется как одна задача;
* невозможно выполнить обязательную проверку и нет безопасной альтернативы;
* команда проверки падает, и ошибку нельзя исправить в рамках текущей задачи;
* Git-команды требуют доступа или авторизации, которых нет в окружении;
* выполнение задачи может привести к потере существующих данных или файлов.

При остановке нужно указать:

1. Что именно заблокировало выполнение.
2. Какая команда или проверка упала, если применимо.
3. Какие файлы уже были изменены, если изменения успели произойти.
4. Что нужно уточнить или исправить.

## 18. Формат финального ответа агента

Финальный ответ должен быть кратким и конкретным.

Обязательно указать:

1. Что было изменено.
2. Какие файлы затронуты.
3. Какие проверки выполнены.
4. Результат проверок.
5. Что не удалось выполнить, если такое было.

Не писать длинные рассуждения.

Не предлагать новые задачи, если пользователь их не просил.

Не скрывать ошибки.

## 19. Главное правило

Проект должен развиваться поэтапно.

Одна задача должна изменять одну ограниченную часть системы.

Главный приоритет — сохранить понятную клиент-серверную архитектуру:

* backend предоставляет REST API;
* frontend работает с backend через HTTP-запросы;
* PostgreSQL хранит данные;
* все данные по процессам обработки, уровню защищённости, модели угроз и техническим мерам защиты принадлежат конкретной карточке ИСПДн.
