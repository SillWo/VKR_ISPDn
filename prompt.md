## Общие правила дизайна для всей платформы

### Область применения
Эти правила применяются ко всем страницам, формам, карточкам, модальным окнам, мастерам создания, реестрам и внутренним модулям платформы.

### Правило 1. Замена switch на checkbox
Во всех местах платформы заменить переключатели с вариантами «Да» / «Нет» на чекбоксы.

Если поле означает бинарный выбор, использовать checkbox.

Пример логики:
- checkbox включён — «Да»;
- checkbox выключен — «Нет».

Нельзя менять смысл поля, имя поля в форме, payload, API или backend-логику.

### Правило 2. Вертикальное выравнивание текста внутри полей
Во всех полях ввода, select-полях, autocomplete и похожих элементах внутренний текст, placeholder и label должны быть визуально выровнены по центру высоты поля.

Проблема, которую нужно устранить: текст внутри поля не должен быть смещён вниз или вверх.

Правка должна быть сделана через общий UI-паттерн или общие стили, если это возможно. Локальные правки допускаются только там, где общего компонента нет.

### Правило 3. Убрать рамки между блоками основного контента
В основной части контента убрать жёсткие рамки, которые визуально разделяют блоки.

Разделение блоков должно строиться по правилу «внутреннего и внешнего»:

- внешний отступ отделяет крупные смысловые блоки друг от друга;
- внутренний отступ показывает содержимое внутри блока;
- визуальное разделение достигается расстоянием, фоном, группировкой и иерархией, а не рамками.

Не нужно полностью убирать карточную структуру, если она нужна для читаемости. Но рамки не должны быть главным способом разделения блоков.

### Правило 4. Кнопки «Далее» и «Назад»
Кнопки «Далее», «Назад» и их логические аналоги всегда размещать рядом друг с другом.

Эти кнопки должны быть визуально выше по иерархии, чем второстепенные действия.

Правила:
- «Далее» — основное действие;
- «Назад» — соседнее навигационное действие;
- второстепенные кнопки не должны конкурировать с ними;
- кнопки не должны быть разнесены в разные части экрана без необходимости.

### Правило 5. Табы
Если в задаче требуется сделать табы, использовать именно Tabs — интерфейс с переключением между разделами.

Нельзя заменять табы обычными заголовками, аккордеонами, карточками или последовательными блоками, если прямо не указано другое.

Tabs должны использоваться для переключения между смысловыми разделами внутри одной формы, страницы или модуля.

Так же важно, что бы в каждой Tabs всегда была кнопка "Далее" и "Назад", которые бы переключали на следующую и предыдущую Tabs соответственно. 

При переходе пользователя с одно Tabs на другую Tabs у него должен открываться новый таб именно с самого начала  

Если пользователь пытается на табе нажать далее, но у него есть другие табы, которые не заполнены, то его автоматически перекидывает на первый слева в интерфейса таб, в котором есть незаполненные поля

## Блок 1. Верхняя аналитическая зона модуля «Технические меры защиты»

### Где
Страница ИСПДн → модуль «Технические меры защиты» → верхняя часть страницы с аналитическими карточками:
- «Уровень защищённости ИСПДн»
- «Меры базового набора»
- «Комментарии по мерам»

### Текущая проблема
В аналитических карточках слишком много пустого пространства справа от диаграмм и текстовых показателей.

Из-за этого карточки выглядят растянутыми, а полезная информация занимает малую часть блока.

Также текст внутри аналитических карточек слишком мелкий относительно размера самих карточек.

### Требуемое изменение
Увеличить размер текста в аналитических карточках:
- заголовки карточек;
- ключевые значения;
- подписи к диаграммам;
- числовые показатели;
- легенды.

Убрать лишнее пустое пространство внутри карточек аналитики:
- перераспределить ширину карточек;
- сделать содержимое более плотным;
- не оставлять большие пустые зоны справа;
- диаграммы и легенды должны занимать карточку сбалансированно.

Карточки должны выглядеть компактнее и информативнее, без ощущения растянутого пустого контейнера.

### Ограничения
Не менять:
- логику расчёта показателей;
- значения аналитики;
- API;
- backend;
- структуру данных;
- названия показателей.

Правка касается только визуального отображения верхних аналитических карточек.

### Проверка результата
На странице «Технические меры защиты» верхние аналитические карточки должны:
- иметь более крупный и читаемый текст;
- не содержать больших пустых зон справа от содержимого;
- сохранять текущие показатели и диаграммы;
- визуально выглядеть плотнее и аккуратнее.

## Блок 2. Таблица мер в модуле «Технические меры защиты»

### Где
Страница ИСПДн → модуль «Технические меры защиты» → нижняя часть страницы с таблицей мер защиты.

### Текущая проблема
Таблица выглядит неравномерно: столбцы распределены по ширине экрана несбалансированно, часть пространства используется неэффективно.

В столбце «Комментарий» сейчас отображается лишняя фраза «Комментарий не заполнен», которая визуально засоряет таблицу.

Статус по приказу «Базовый набор» выглядит слишком контрастным и конкурирует с более важными элементами интерфейса.

В столбце «Фактический статус» под каждым select отображается кнопка «Сохранить», из-за чего таблица перегружена повторяющимися кнопками.

### Требуемое изменение
Выровнять таблицу так, чтобы все столбцы были визуально сбалансированы и равномерно заполняли доступную ширину экрана.

Для столбца «Комментарий» использовать такие правила отображения:
- если комментарий есть — показывать текст комментария;
- если комментарий требуется — показывать бейдж/метку «Требуется комментарий»;
- если статус корректный и комментарий не нужен — показывать прочерк;
- фразу «Комментарий не заполнен» больше не отображать.

Статус по приказу сделать менее контрастным:
- оставить его читаемым;
- снизить визуальный акцент;
- он не должен конкурировать с фактическим статусом и предупреждением «Требуется комментарий».

В столбце «Фактический статус» убрать кнопку «Сохранить».

Фактический статус должен сохраняться автоматически после выбора значения в раскрывающемся списке.

### Ограничения
Не менять:
- список мер;
- коды мер;
- текст содержания мер;
- бизнес-логику определения базового набора;
- логику определения необходимости комментария;
- API, если текущий endpoint уже позволяет сохранять статус по одному действию;
- backend без отдельной необходимости.

Если для автосохранения уже есть подходящий frontend mutation — использовать её.  
Если текущая логика сохранения завязана только на кнопку, перенести вызов сохранения на событие выбора статуса без изменения структуры данных.

### Проверка результата
В таблице мер защиты:
- столбцы выглядят ровно и сбалансированно;
- повторяющиеся кнопки «Сохранить» отсутствуют;
- статус сохраняется после выбора значения;
- «Комментарий не заполнен» нигде не отображается;
- при необходимости комментария отображается только «Требуется комментарий»;
- если комментарий не нужен и его нет, отображается прочерк;
- статус по приказу визуально спокойнее и менее контрастный.


## Блок 3. Верхняя карточка страницы «Карточка ИСПДн»

### Где
Страница ИСПДн → верхняя карточка с названием ИСПДн, подписью «Карточка ИСПДн #...», кратким описанием, ответственным и статусом.

### Текущая проблема
В верхней карточке нарушена визуальная иерархия: подпись «Карточка ИСПДн #... » сейчас находится под названием, хотя должна работать как менее значимый надзаголовок.

Краткое описание ИСПДн дублируется в верхней части страницы и в блоке «Основные сведения», из-за чего верхняя карточка перегружена.

Поле «Ответственный» сейчас отображается обычной строкой текста и визуально теряется.

### Требуемое изменение
Перестроить верхнюю карточку ИСПДн:

1. Текст «Карточка ИСПДн #... » расположить над названием ИСПДн.
2. Сделать «Карточка ИСПДн #... » менее контрастным: меньший размер, спокойный серый цвет, вторичная типографика.
3. Название ИСПДн оставить главным текстовым элементом карточки.
4. Убрать краткое описание ИСПДн из верхней карточки.
5. Краткое описание должно остаться только в блоке «Основные сведения».
6. Поле «Ответственный» оформить как тег/chip:
   - компактный бейдж;
   - визуально отделён от обычного текста;
   - не должен конкурировать со статусом ИСПДн.
7. Статус ИСПДн в правой части карточки оставить.

### Ограничения
Не менять:
- данные ИСПДн;
- API;
- backend;
- маршруты;
- логику статуса;
- содержимое блока «Основные сведения»;
- сохранение формы.

Правка касается только визуального отображения верхней карточки ИСПДн.

### Проверка результата
Верхняя карточка должна выглядеть так:
- сначала менее контрастная подпись «Карточка ИСПДн #... »;
- ниже крупное название ИСПДн;
- краткого описания в верхней карточке нет;
- ответственный отображается как тег;
- статус ИСПДн остаётся справа;
- краткое описание доступно только в блоке «Основные сведения».

## Блок 4. Блок «Актуальные задачи ИСПДн» в карточке ИСПДн

### Где
Страница ИСПДн → блок «Актуальные задачи ИСПДн».

### Текущая проблема
Сейчас задачи отображаются карточками, из-за чего список занимает много места и плохо сканируется.

Статус задачи отображается как обычный тег без цветового индикатора, хотя в основном модуле задач уже есть цветовая логика статусов.

Событие сейчас отображается строкой текста, а не отдельным визуальным элементом.

Теги статуса, важности, дедлайна и ответственного расположены внутри карточки слева и перегружают основной текст задачи.

### Требуемое изменение
Преобразовать список актуальных задач ИСПДн в таблицу.

Столбцы таблицы:
1. «Задача»
2. «Статус»
3. «Важность»
4. «Дедлайн»
5. «Ответственный»

В столбце «Задача» отображать:
- название задачи;
- событие задачи отдельным тегом;
- краткое описание задачи, если оно сейчас отображается и доступно в данных.

Статус задачи оформить с цветовым индикатором по тем же правилам, что в основном модуле «Задачи и несоответствия»:

- «Ожидает выполнения» — синий;
- «В работе» — жёлтый;
- «Выполнена» — зелёный.

Важность задачи оформить по той же цветовой логике, что в основном модуле задач:

- «Без важности» — серая;
- «Низкая» — светло-зелёная;
- «Средняя» — жёлтая;
- «Высокая» — красная;
- «Критическая» — фиолетовая.

Теги статуса, важности, дедлайна и ответственного должны быть компактными и располагаться в соответствующих правых столбцах таблицы, а не внутри основного текста задачи.

Событие задачи вынести в отдельный тег внутри столбца «Задача».

При нажатии на название задачи пользователь должен переходить к этой задаче в основном модуле «Задачи и несоответствия».

### Ограничения
Не менять:
- backend;
- API;
- логику получения задач;
- логику статусов;
- логику важности;
- фильтрацию актуальных задач;
- маршруты, если уже существует маршрут к задаче или событию в основном модуле.

Если прямого маршрута к конкретной задаче нет, переход должен вести в основной модуль задач с сохранением максимально возможного контекста: выбранная ИСПДн, событие или задача, если это уже поддержано текущим frontend.

### Проверка результата
Блок «Актуальные задачи ИСПДн» должен отображаться как компактная таблица.

В таблице:
- задачи легко сравниваются по статусу, важности, дедлайну и ответственному;
- событие отображается отдельным тегом;
- статус имеет цветовой индикатор как в основном модуле задач;
- важность имеет цвет как в основном модуле задач;
- повторяющиеся карточки задач больше не используются;
- клик по задаче ведёт пользователя в основной модуль задач.

## Блок 5. Основной модуль «Задачи и несоответствия»

### Где
Глобальный модуль «Задачи и несоответствия» → список событий и таблицы задач внутри событий.

### Текущая проблема
В карточке события слишком много крупных кнопок, из-за чего правая часть перегружена.

Кнопка «Скрыть задачи» занимает лишнее место, хотя её действие можно заменить компактной иконкой раскрытия.

Кнопки «Перейти к ИСПДн» и «Добавить задачу» имеют разную ширину и переносят текст на несколько строк.

Иконки действий в таблице задач расположены вертикально, из-за чего строка становится визуально тяжелее.

Название связанной ИСПДн отображается обычным текстом и плохо считывается как отдельная сущность.

Дата и время создания события тоже отображаются обычной строкой, хотя это метаданные события.

### Требуемое изменение
Убрать кнопку «Скрыть задачи».

Функционал раскрытия/скрытия задач перенести в иконку раскрывающего списка:
- иконка должна находиться в нижней части блока события;
- по нажатию иконка раскрывает или скрывает таблицу задач;
- состояние раскрытия должно быть визуально понятно.

Кнопки «Перейти к ИСПДн» и «+ Добавить задачу» сделать фиксированного размера:
- текст внутри кнопок должен помещаться в одну строку;
- кнопки должны быть одинаково аккуратными и не ломать сетку карточки события;
- описание события должно динамически занимать оставшееся пространство и подстраиваться под размер блока с кнопками.

В таблице задач иконки действий разместить в одну строку:
- редактирование;
- удаление;
- другие действия, если они есть.

Название ИСПДн внутри события оформить как кликабельный тег:
- тег ведёт на карточку связанной ИСПДн;
- для разных ИСПДн использовать разные цвета тегов;
- цвет должен быть спокойным и не конфликтовать с цветами статусов и важности;
- если событие не связано с ИСПДн, показывать нейтральный тег «Без привязки к ИСПДн» без ссылки.

Дата и время создания события должны отображаться как отдельный тег:
- компактный;
- менее контрастный;
- визуально относится к метаданным события.

### Ограничения
Не менять:
- backend;
- API;
- структуру данных задач и событий;
- логику фильтрации;
- логику создания задач;
- логику удаления и редактирования задач;
- статусы задач;
- важность задач;
- маршруты, если переход к карточке ИСПДн уже реализован.

Если для разных цветов ИСПДн нет готового механизма, цвет можно вычислять на frontend по id ИСПДн детерминированно, чтобы одна и та же ИСПДн всегда имела один и тот же цвет.

### Проверка результата
В основном модуле «Задачи и несоответствия»:
- кнопки «Скрыть задачи» больше нет;
- задачи раскрываются и скрываются через компактную иконку в нижней части карточки события;
- «Перейти к ИСПДн» и «+ Добавить задачу» не переносят текст на вторую строку;
- описание события не ломает расположение кнопок;
- иконки действий в таблице задач стоят в одну строку;
- название ИСПДн отображается как кликабельный цветной тег;
- дата и время создания события отображаются как тег.

## Блок 6. Глобальный модуль «Документы»

### Где
Глобальный модуль «Документы» → список доступных документов уровня организации.

### Текущая проблема
Сейчас документы отображаются длинным вертикальным списком карточек. Из-за этого страница быстро становится перегруженной, особенно при добавлении новых документов.

Внутри карточек есть дополнительные блоки с пользовательскими данными, но визуально они выглядят как отдельные вложенные секции и усложняют восприятие.

### Требуемое изменение
Переработать отображение документов через Tabs.

Каждый доступный документ должен быть отдельным табом:
- «Уведомление в Роскомнадзор о намерении осуществлять обработку персональных данных»;
- «Уведомление в Роскомнадзор об изменении сведений...»;
- «Положение об организации и обеспечении защиты персональных данных»;
- «Положение об обработке персональных данных»;
- остальные документы, если они есть в текущем реестре документов.

При выборе таба пользователь видит форму генерации только выбранного документа.

Все дополнительные данные, которые пользователь должен ввести вручную для генерации выбранного документа, должны отображаться в отдельном блоке без заголовка.

Правила для блока ручного ввода:
- не добавлять отдельный заголовок вроде «Ручные данные»;
- показывать только набор полей с понятными названиями;
- поля должны быть визуально сгруппированы;
- если ручных данных для документа нет, блок ручного ввода не показывать;
- кнопка генерации документа должна относиться к выбранному табу.

### Ограничения
Не менять:
- backend;
- API генерации документов;
- document codes;
- логику DocumentRegistry;
- шаблоны документов;
- названия документов;
- manual fields;
- правила формирования контекста документов.

Правка касается только frontend-отображения глобального модуля «Документы».

### Проверка результата
В глобальном модуле «Документы»:
- документы больше не отображаются длинным вертикальным списком;
- каждый документ доступен через отдельный tab;
- при переключении tab меняется форма выбранного документа;
- ручные поля отображаются отдельным блоком без заголовка;
- если ручных полей нет, пустой блок не отображается;
- генерация документа работает так же, как раньше.
